# 两个聊天节点，共用一份源码

两个聊天节点分别使用 `../ChatServer/ChatServer.cpp` 与 `../ChatServer2/ChatServer.cpp` 入口。
本公开仓库仅发布源码/资源，不包含本机 VS 工程或公共属性表；请分别建立工程并加入本目录公共实现、头文件路径，配置参考各节点 `config.example.ini`。
源码和源文件清单只维护一次；每个工程仍独立编译出自己的程序，不共享进程内存、业务线程或在线会话。

原两份工程中的公共源码已迁入本目录。采用原 ChatServer 中包含 `last_message_id`、`last_chat_time` 的会话实现；没有合并或改写两节点配置。
日志身份由各工程的 `CPPCHAT_NODE_NAME` 编译定义区分，Redis 路由身份仍取各自 `SelfServer.Name`。
新增公共 `.cpp/.h` 时同步自己的两个工程文件清单，不在两个节点目录复制公共源码。

## 发布与版本

本目录在公开仓库中与两个节点入口统一版本管理，不包含独立 `.git` 或本机恢复标签。
两个节点及依赖公共代码的 GateServer、StatusServer、ResourceServer 应配套更新。

## 职责

- `ChatServerApp`：两个入口共用的启动、关闭流程。
- `CServer/CSession`：连接、封包、发送队列、心跳与会话清理。
- `LogicSystem`：登录状态校验、请求分发与回包。
- `SessionService`：登录校验、资料/好友初始化、登录锁、旧会话处理、凭证注册/绑定和心跳好友快照；不解析 TCP JSON、不直接发送回包。
- `RequestContract`：可选 `request_id` 的 JSON 包络校验与回传；登录声明关联能力，业务通知不充当请求响应。
- `BusinessExecutor`：有上限的连接分片队列；同连接 FIFO、不同分片并行、耗时统计和安全排空。
- `UserService`：当前资料查询、资料更新与缓存失效；不缓存密码。
- `FriendService`：申请、接受、删除、标签和好友通知；TCP 与 gRPC 共用通知规则。
- `MessageService`：消息权限、资源归属、持久化、通知、会话和历史访问。
- `ChatGrpcClient/ChatServiceImpl`：跨服 RPC 发起和接收适配。
- `MysqlMgr/MysqlDao`：保留数据库访问入口和公开接口。`MysqlDao.cpp` 管配置/池生命周期，`MysqlDaoUsers/Contacts/Messages.cpp` 按领域组织原 SQL 实现，`MySqlPool` 与内部 `MysqlDaoSupport` 共用连接守卫、事务和结果读取。
- `ContactTags`：各入口共用的标签规范化规则。

DAO 分组只是实现边界，不是三个独立数据库或连接池。接受好友、建立私聊及初始消息继续在同一连接、原事务范围提交；删除好友也留在好友领域，没有恢复单接口 `DeleteFriendService`。本次迁移不改 SQL/表结构，不增加无意义的 Repository 转发层。连接池借用超时不等于 SQL 命令超时。

新增协议字段为可选的 1-64 字节字符串 `request_id`；合法标识在正常/业务错误/未登录拒绝回包中原样返回。成功登录包含 `request_correlation=true`。客户端每次尝试生成新标识，文本消息的 `unique_id` 去重规则不变；旧客户端缺少标识仍可请求。完整兼容规则见客户端 `docs/protocol-contract.md`。

## 健康与凭证

`ServicePolicy.h` 由 StatusServer 和两个聊天工程共同使用。

| Redis 键 | 用途 | 默认有效期 |
|---|---|---|
| `chat_node_<节点名>` | 节点实例 ID、已登录人数 | 30 秒，每 10 秒更新 |
| `utoken_<uid>` | HTTP 登录分配的待登录凭证 | 5 分钟，建立会话后消费 |
| `resource_token_<uid>` | 活跃会话凭证，兼容资源服务 | 1 小时，由在线会话续期 |
| `usession_<uid>`、`uip_<uid>` | 当前会话 ID、节点路由 | 同活跃会话有效期 |

StatusServer 仅选择健康键存在且数据有效的已启用节点，以已登录人数比较，人数相同则轮换。
健康键过期后节点不再参与分配；没有健康节点时返回错误，不回退到可能已停机的节点。
重新登录时，旧节点健康租约已过期则接管旧路由，不再因向宕机节点发送踢下线 RPC 而阻断登录；旧租约仍有效时保留踢下线流程。
健康记录包含启动实例 ID，节点不能覆盖另一个仍持有租约的同名实例；正常退出只删除自身的健康记录。

Token 不再保存在 StatusServer 的内存映射中。Redis 必须可用；StatusServer 重启本身不会清掉 Redis 中仍有效的凭证。
会话注册用 Lua 原子校验凭证、发布会话和路由、消费待登录凭证。
续期与清理均比较会话 ID，旧连接不得续期或删除新连接的凭证。
本地用户绑定与断线清理互斥；登录处理中断线时撤销刚注册的会话，一个 TCP 连接不能切换已登录用户。
没有有效期的旧 Token 被拒绝，升级后客户端需要重新登录；ResourceServer 也执行相同的有效期要求。
Redis 的实际持久化和高可用依赖部署配置，本次没有自动更改这些配置。

## 超时与可靠性边界

聊天通知 RPC 的调用超时为 3 秒，借用 Stub 最多等待 3 秒；原聊天登录校验保留 5 秒超时。
网关节点分配 RPC 加入 3 秒调用超时；邮件验证码 RPC 保留原 20 秒调用超时，避免改变邮件发送语义。
网关借用 Stub 也有等待上限。聊天/状态服务 Redis 建连、命令和借用连接设置 3 秒上限；资源服务 Redis 使用 2 秒上限。
共享 MySQL 连接池借用等待上限为 3 秒，但这不等于每条 SQL 都有 3 秒查询上限。

聊天业务队列上限为 10000。队列满时拒绝该连接的请求并断开；发送队列仍沿用原上限。
已关闭连接的排队请求不再执行，业务回调异常会记录日志并清理连接。
消息写入数据库成功与实时通知成功分开处理；跨服通知失败会记录日志，不能把 RPC 失败覆盖为成功。
已提交业务依靠原有登录列表、心跳好友快照或历史补拉恢复，不声称具备事务消息、持久通知重试或收件人送达确认。
网络 I/O 仍异步；业务按不可变连接 UUID 分片，同一连接的登录和后续请求始终在同一 FIFO 队列执行。
不同分片并行，同一分片上的其他连接仍可能受慢任务影响；不承诺全局顺序或两个节点之间的请求顺序。
数据库事务、成员权限、消息 UUID 去重、登录分布式锁和会话 ID 清理保护继续承担跨线程/跨节点一致性职责。

可在两个节点各自的 `config.ini` 增加：

```ini
[Business]
Workers=4
MaxConnections=4096
```

`Workers` 支持 1-16，默认 4；设为 1 可退回单业务线程。共享排队上限为 10000，运行中的任务不计入排队数，最多再有 Workers 个。
连接数上限包含未登录连接；满时关闭新连接。每 10 秒记录 queued/active/completed/rejected/failed、高水位、平均/最大排队和执行耗时。
这些是本进程累计指标，不是 P95/P99；completed 包括正常回包的业务拒绝，failed 表示执行器兜底捕获的异常。
心跳/Redis 维护移至独立单线程、最多一个待处理快照，不阻塞 acceptor 的 I/O 循环；维护长期滞后仍会导致健康租约失效。
正常停机先停止接收、排空已接受任务，再按会话 ID 清理本节点凭证。退出时间仍可能受未设置命令超时的 SQL 影响。

## 构建与部署注意

2026-10-06 的连接线程边界加固：`CSession` 的启动、异步读写和 socket 关闭均使用同一个 strand。
`Send` 在调用线程先检查有界队列，再只为开始发送调度任务，避免把队列容量检查推迟到无上限的 executor 队列中。
写回调持有对应 `SendNode`；关闭清空等待队列时，不会释放仍供异步写使用的缓冲区。
踢下线通知与“发送完成再关闭”的标记一起入队；发送积压达到上限时断开慢消费者，不再悄悄丢弃后续回包。
进入通知排空状态的连接对业务分发视为已关闭，不能继续执行排队请求或重新绑定身份；物理 socket 保留到末尾通知发送完成。
主线程必须在连接 I/O 仍运行时等待 socket 关闭完成，才能停止 I/O 池；不能从 I/O 线程调用阻塞的 `CloseSessions`。
第二阶段已接入先停准入、排空已接纳业务、限时排空发送、物理关闭连接，再停止 I/O 池的退出顺序。
连接停机写排空期限 5 秒，踢下线通知期限 3 秒；不能保证断网或慢客户端收到消息，也不承诺整个进程 5 秒退出。
断线凭证清理交给独立的有界执行器，Lua 仍按旧会话 ID 校验，不会删除重新登录的凭证。
等待清理最多 5 秒后丢弃尚未执行的清理任务；正在执行的 Redis 调用仍安全等待结束。
失败/跳过的凭证清理依赖原有最长 1 小时活动租约过期，不能当作即时凭证撤销保证。
正在执行的 SQL 没有命令级超时，退出仍可能等待数据库；这个限制另需处理。

GateServer 复用本目录的 `BusinessExecutor`，数据库、密码校验和同步 RPC 路由进入受限业务线程。
回包再 post 到连接 strand；超时先关闭 socket，已过期的排队请求不执行业务，正在执行的业务不承诺回滚。
其可选 `[Business] Workers=4`（1-16）、`QueueLimit=256`（1-65536）；不修改现有机器配置，缺失时使用默认值。
网关请求正文限制 32 KiB、头部限制 8 KiB，排队满返回 HTTP 503；`[GateServer] RequestTimeoutSeconds=60` 可配置为 1-300 秒。
正文大小限制针对现有认证/验证码 JSON 路由，不用于资源上传服务。
网关活动连接默认上限 1024，可配置 `[Business] MaxConnections=1024`（1-100000）。
停机关闭未接纳业务的空闲/半包连接，已接纳请求仍按原请求期限与额外 5 秒写排空期限收尾；最后才停止 I/O。
两种服务的依赖持有者覆盖异常启动，取消中的 accept 回调先处理完，再销毁其 socket 所属的 I/O 池。
本轮进度及隔离测试证据见客户端 `docs/architecture-hardening-20261006.md`。

源码包应同时包含两个节点工程及同级 `ChatServerShared` 目录；两台机器可以分别构建各自工程。
部署运行只需要各自构建产物及依赖、配置，不需要把共享源码目录当作运行时服务。
两个节点必须使用不同 `SelfServer.Name`、监听端口或主机地址；StatusServer 中的名称和客户端可达地址要一致。
跨机器部署要把 `127.0.0.1` 改成相应可达地址，仍共享同一业务 Redis/MySQL；本次保留现有配置。
进程工作目录应是包含相应 `config.ini` 的目录。现有构建后拷贝配置流程保留。

两个聊天工程各为 24 个公共编译单元加独立入口。本轮已实际执行 x64 Debug/Release 编译和链接，并修复 Redis 超时所需的 Windows timeval 头文件。
原有动态 vcpkg triplet 与手写静态 MySQL/hiredis 库目录保留；本机组合能编译链接，不表示其他依赖版本或机器的 ABI 一定兼容。
编译产生的第三方头文件警告没有作为本项目源码错误处理；本轮不包含 Win32 构建验证。

本次需重新构建并协调更新 GateServer、StatusServer、两个 ChatServer 和 ResourceServer。
旧聊天节点不发布新健康键，不能与新 StatusServer 混用；请在维护窗口一起更新，再让客户端重新登录。
没有修改现有 gRPC 消息字段或数据库结构，无需为这次结构调整执行新 SQL 迁移。

## 群聊

`MysqlDaoGroups.cpp` 负责群资料与成员事务；`LogicSystem` 保留协议适配，
`MessageService` 复用消息去重、分页历史和原 gRPC 跨节点投递。
群主可邀请自己的好友、移除成员、改群名、转让群主和解散；成员可发文字/表情和退群。
成员互相不必是好友。最多 32 人，群名 1–64 UTF-8 字节，不接受控制字符或纯空白。
邀请成员可读取该群全部历史；退群、被移除或解散后，服务器拒绝后续读取和发送。
已下载的本机历史不会远程擦除，重新入群可继续同步。

群变更和发送持有同一个群行锁，权限以数据库当前成员关系为准。
创建使用 `(creator_uid, creation_key)` 及规范化初始参数去重；传输重试改变 request_id，
保留 creation_key。解散保留停用的群元数据和消息以避免旧创建请求复活群。
群消息复用旧 chat_message 表：接收者列使用 sender_id 作为兼容非空外键的内部标记，
只有已锁定的 active 群与成员记录能授权该写入路径，私聊不能借此绕过好友检查。
群消息落库后先回复成功，再向当前成员逐一投递；实时投递失败可由历史补拉恢复。
群图片尚未开放，现有 ResourceServer 仍只授权两人资源，服务端拒绝群图片元数据。
群资料及成员变化通过客户端 10 秒会话刷新和群管理查询恢复，群消息仍实时推送。

已有 MySQL 库需由维护账号先执行 `database/mysql/20261018_group_chat.sql`，
然后配套更新两个聊天节点和客户端；运行账号不增加 DDL 权限，不重导全库。

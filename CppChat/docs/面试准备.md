## 90 秒项目介绍

> 这是一个基于 Qt Widgets 和 C++ 服务端的即时通信学习项目。我围绕账号体系、聊天连接接入和客户端界面进行了实现。
>
> 客户端通过 HTTP 请求网关，完成验证码、注册和邮箱密码登录。网关通过 gRPC 调用验证码服务和状态服务，用户数据存到 MySQL，验证码存到 Redis 并设置有效期。账号验证成功后，客户端获取聊天节点地址和 Token，再建立 TCP 连接并提交 uid、Token，由服务端校验。
>
> 网络部分使用 Boost.Asio，TCP 应用层协议采用两字节消息 ID、两字节消息体长度和 JSON 消息体，处理分段接收和连续多包。界面部分实现了文本、图片气泡以及滚动和窗口交互。
>
> 当前重点完成的是账号和连接认证相关代码，以及聊天界面。双人消息转发、消息持久化和断线恢复是后续完善方向。

## 高频问题与回答

### 1. 从点击登录到进入聊天页，完整过程是什么？

1. LoginDialog 校验输入，通过 HttpMgr 向 `/user_login` 提交 email、passwd。
2. GateServer 查询 MySQL，校验邮箱对应的密码。
3. GateServer 调用 StatusServer 的 GetChatServer，获取节点地址和 Token，返回给客户端。
4. TcpMgr 连接 ChatServer；连接成功后，LoginDialog 发送 ID_CHAT_LOGIN，携带 uid、token。
5. ChatServer 的 CSession 读出完整消息，放入 LogicSystem 队列。
6. LogicSystem 调用 StatusServer::Login 校验 uid、token，并发送登录回包。
7. TcpMgr 处理 ID_CHAT_LOGIN_RSP，成功后更新 UserMgr，并发信号切换页面。

TCP 连接成功只说明通信通道建立；应用层身份校验成功才说明业务登录成功。当前 mainwindow.cpp 仍直接进入聊天页，这是 UI 测试入口，不能拿它证明完整登录联调通过。

### 2. 为什么分成四个服务？小项目有没有必要？

GateServer 处理 HTTP 接入与账号业务；VerifyServer 生成、缓存验证码并发送邮件；StatusServer 分配聊天节点并校验 Token；ChatServer 管理 TCP 连接及已实现的登录消息处理。

这样方便分别学习和演进，也能隔离部分职责。代价是多进程部署、跨服务超时、状态共享、错误定位都更复杂。对小规模产品，单体也可能更合适，不把拆服务本身当作性能成果。

### 3. 为什么同时使用 HTTP、TCP 和 gRPC？

HTTP/JSON 适合账号操作的请求响应，也方便排查；自定义 TCP 协议为后续持续消息收发提供连接基础；gRPC/Protobuf 定义内部服务接口，支持 C++ 与 Node.js 协作。

注意 HTTP 和 TCP 不在同一层。本项目的 HTTP 通信也使用 TCP；这里比较的是 HTTP 应用协议与自定义 TCP 应用协议。HTTP 本身可以复用连接，不能说每次 HTTP 请求都必须重连。

### 4. TCP 为什么会有“粘包、半包”？怎么处理？

TCP 提供有序字节流，不保留每次 send/write 的应用消息边界。接收方一次读取可能只拿到半条，也可能拿到多条。

客户端把 readyRead 收到的字节追加到 `_buffer`：不足四字节就等待；包头完整后读出消息 ID 和长度；消息体不足时保存等待状态；完整后取出消息交给处理函数，再循环解析剩余数据。服务端则先凑够四字节头，再按长度凑够消息体。

口头示例：A 包头四字节、包体六字节。第一次收到两字节，等待；第二次又收到五字节，总共七字节，包体仍差三字节；第三次收到 A 的剩余三字节和完整 B，处理 A 后继续处理 B。

追问：空包、非法长度、未知消息 ID、恶意慢速发送、断线后残留缓冲分别怎么处理？说明当前检查与计划增强的部分。

### 5. 为什么消息长度用 UTF-8 字节数？为什么用大端序？

网络发送的是字节；QString::size() 是 UTF-16 代码单元数量，不能直接作为 UTF-8 包体长度。先 toUtf8()，再取字节数，例如“你好”的 UTF-8 内容是六字节。

大端序是协议双方约定的字段编码方式，让不同主机一致解释两字节整数。客户端使用 QDataStream::BigEndian，服务端进行网络序转换。

当前客户端长度字段用 quint16，服务端包体上限为 16 KiB（MAX_LENGTH），资源包体上限为 60 KiB。客户端普通请求仍主动控制在 2 KiB 并分段，资料包控制在 16000 字节；因此不能将字段能表达的 65535 字节当成实际业务上限。图片分块为 32 KiB，图片上限为 20 MiB。

### 6. readyRead 或 async_read_some 会一次读满吗？async_write 成功说明什么？

readyRead 表示当前有数据可读，async_read_some 返回本次读取的部分字节，都不保证获得一条完整应用消息。项目通过缓冲或继续异步读取来组帧。

async_write 是组合操作，成功时完成指定缓冲区的写出；这不代表对方应用已解析、落库或展示。需要这些业务保证时，必须设计相应的确认语义。

### 7. 为什么服务端要有发送队列？

同一连接的多个业务响应需要依次写出，并保持异步写入所引用的数据有效。CSession 先把消息放入 send_queue_；已有写操作时只入队；队首完成后出队并继续发送下一条。

当前发送队列有上限，满了会记录并拒绝新消息；还没有由此形成的业务重试或可靠投递保证。

### 8. 项目的多线程模型是什么？

ChatServer 的 AsioIOServicePool 创建多个 io_context，各由一个工作线程执行 run()，新会话轮流取得 io_context。CSession 负责收发和组帧，把完整消息交给 LogicSystem。

LogicSystem 当前只有一个业务消费线程，通过条件变量等待队列。这样业务回调执行不会直接占用原来的网络读取回调，但一个业务请求耗时长仍会阻塞后续业务消息。

GateServer 的网络收发虽然异步，路由中仍执行同步数据库和 gRPC 调用，因此仍可能占用其 I/O 工作线程。不要把“用了 async”解释成“所有操作都不阻塞”。

### 9. 如何提高吞吐量？瓶颈在哪里？

先测量：活跃连接数、请求延迟、业务队列长度、数据库等待时间、RPC 延迟、CPU 和内存，再定位瓶颈。

当前代码可以指出的潜在瓶颈包括同步外部调用、单一逻辑线程、逻辑队列没有入队容量检查，以及客户端不断创建消息 QWidget。后续可评估有界业务线程池、按会话分片处理、超时与过载控制、界面分页或模型视图。多个线程处理业务时，还要维护同一会话的顺序，不能简单无限加线程。

这些是分析和改进方案，不是已经压测证明的结果。

### 10. 条件变量为什么要带谓词？wait 时锁还占着吗？

谓词通常是“停止了，或者队列不为空”。wait 在等待期间释放互斥锁，醒来后重新获得锁并检查条件，处理虚假唤醒和其他线程抢先消费的情况。

LogicSystem 在锁内取出消息，离开锁的作用域后执行业务，避免慢回调一直占着队列锁。关闭时设置停止标记并唤醒等待线程。

### 11. 连接池和线程池有什么区别？gRPC Stub 池是什么？

连接池复用 MySQL/Redis 等访问资源；线程池复用任务执行线程。Stub 池管理远程调用代理对象的借还，不负责替你运行一组业务线程。

当前 BorrowStub 会等待可用对象；RPC 调用仍同步执行。RPC deadline 也不能直接使不带超时的条件变量等待返回，需要分别考虑资源借用等待与远程调用时间。

### 12. RAII 用在哪里？为什么捕获 shared_ptr？

RAII 把资源释放放到对象析构：lock_guard 自动解锁，MySqlConnectionGuard 自动归还连接。这样普通提前返回或异常展开时也能执行清理。

CSession 的异步回调捕获 shared_from_this() 得到的 shared_ptr，保证回调执行期间 Session 仍存在。只捕获裸 this 不会延长对象生命。

shared_ptr 解决所有权，不自动保护对象内部成员并发访问；循环持有会导致不能释放，应按实际所有权关系使用 weak_ptr。shared_from_this 要求对象已经被适当的 shared_ptr 管理，不能随意在构造函数内使用。

### 13. 单例是线程安全的吗？

客户端 Singleton 用 once_flag、call_once 保证一次初始化，每个模板参数类型分别有实例。初始化线程安全，不代表实例中的每个函数和成员都线程安全。

涉及 QObject 的单例还要关注创建线程与线程归属。当前友元/私有构造方式也解释了为什么不能机械地把 `shared_ptr<T>(new T)` 换成 make_shared：构造权限检查位置不同。

### 14. Redis 和 MySQL 分别存什么？验证码怎么过期？

MySQL 保存用户信息与密码验证材料；VerifyServer 将验证码存到 Redis，设置 180 秒 TTL。代码通过一条 SET ... EX 命令同时写值和过期时间，避免两条命令之间失败留下不失效的验证码。

GateServer 注册时读取并比较验证码，数据库注册成功后删除验证码。完整过程跨越 Redis 与 MySQL，不是一项原子事务；并发校验、重复提交和删除失败仍值得进一步设计。

TTL 表示过期，不等于限流。验证码发送频率、错误尝试次数、并发生成的一致性是另外的问题。

### 15. 密码和 Token 分别是什么？

密码用于首次账号认证。当前 MysqlDao 使用随机盐和 PBKDF2-HMAC-SHA256 生成验证材料，代码中的迭代次数是 120000；这是本项目参数，不是这里给出的通用安全参数推荐。登录时读取盐与参数重新计算并比较。

Token 是账号认证成功后，客户端向 ChatServer 提交的后续认证凭据。当前由 StatusServer 生成随机 UUID 字符串，并在内存映射中保存 uid 到 Token；它不是 JWT，也没有看到过期时间实现。

服务器重启会丢失这些映射，多实例状态不会自动共享；后一次同 uid 的 Token 会覆盖前一个，但这不等于已经踢掉旧的 TCP 会话。密码存储保护和网络传输保护也是两回事。

### 16. StatusServer 真的是实时最小连接数负载均衡吗？

当前策略选择 con_count 最小的节点，并在分配时加一。当前实现中没有对应的断开减计数或心跳上报机制，因此它更接近按累计分配次数均衡，不能声称准确反映实际在线人数。

如果扩展，需要考虑节点健康、连接统计上报、失效检测、分配失败和恢复；这些属于后续设计。

### 17. HTTP 响应如何回到正确页面？

HttpMgr 用 QNetworkAccessManager 发出请求，在 QNetworkReply::finished 中取得结果，并带着捕获的 ReqId、Modules 发出完成信号，再分发给登录、注册或重置页面。

这里的 ReqId、Modules 是客户端内部路由信息，不会自动放进 HTTP 请求体。TCP 包头里的消息 ID 则属于实际网络协议。

同一个接口被并发请求时，类型 ID 不等于唯一请求 ID；如需区分同类多次请求，还要保留独立上下文或请求序号。

### 18. Qt 信号槽一定异步吗？能直接在子线程改界面吗？

不一定。直接连接会直接调用槽；队列连接把调用交给接收对象所属线程的事件循环。自动连接取决于发射时所在的线程与接收对象线程归属。

界面更新应回到 GUI 线程。跨线程传递结果可以使用带接收对象上下文的信号槽，并注意自定义参数类型及生命周期；不要把网络异步误认为自动新建后台线程。

QNetworkReply 用 deleteLater 请求延迟删除，与 QObject 的事件处理配合；父子对象关系和智能指针所有权需要一致规划，不能对同一对象重复拥有。

### 19. GIF、滚动动画为什么会卡住？

绘制、输入和定时器都依赖 GUI 线程继续处理事件。若槽函数执行长时间循环、同步等待或 sleep，即使调用了显示和动画启动，后续帧也可能无法及时绘制。

耗时工作需要合理异步处理或移到工作线程；QTimer::singleShot(0, ...) 只是延后调度，不会把耗时任务自动搬到另一个线程。

### 20. 文本、图片气泡具体怎么实现？

BubbleFrame 在 paintEvent 中用 QPainter 绘制圆角矩形和左右三角形，根据自己或对方设置方向、颜色和布局边距。

TextBubble 使用只读 QTextEdit，借助 QFontMetricsF 估计段落宽度，结合 QTextDocument 的文档边距、布局边距与实际文本布局高度确定尺寸。PictureBubble 先按比例缩放图片，再由 QLabel 展示。

当前图片展示读取本地内容，不代表图片经过了网络上传。当前文本高度调整发生在绘制事件过滤中，后续可评估改由内容或宽度变化驱动，减少绘制阶段布局调整。

### 21. 滚动动画和聊天记录很多时怎么处理？

当前 ChatView 使用 QScrollArea 和垂直布局展示消息，对原生滚动条 value 做 QPropertyAnimation。连续滚轮输入累加目标位置，拖动滑块时停止动画，避免两者同时修改位置。

每条消息对应 QWidget，消息很多时对象数、布局、图片内存会增加。分页加载、限制保留数量、模型与委托绘制是可评估的后续方案。不要把当前布局称为已经实现虚拟列表。

### 22. 无边框窗口有哪些难点？

去掉系统边框后，需要自己处理标题栏按钮、拖动、缩放边缘和状态图标。当前 MainWindow 使用事件过滤与 startSystemMove/startSystemResize，并在 Windows 分支保留相关原生窗口样式、处理非客户区，从而配合系统窗口行为。

追问重点：事件过滤返回 true 表示什么？Qt 坐标与原生像素坐标如何区分？最大化为什么要考虑工作区与任务栏？跨平台代码如何隔离？

### 23. 怎么保证消息不丢、不重复、顺序正确？

当前尚未实现双人消息业务和这些应用层保证。TCP 的传输能力不能替代应用落库与业务确认。

设计题可回答：给消息唯一 ID；明确“服务端受理/已保存/对端收到/已读”的不同状态；超时重试时用 ID 去重；使用会话内序号辅助排序和断线补拉；客户端显示待发送、失败等状态。ACK 发在落库前还是后取决于确认的语义，不能把所有成功合成一个状态。

### 24. 讲一个有价值的问题定位案例。

从你实际参与过的问题选一个，按“现象→证据→原因→修改→验证”说明。可选当前源码中的案例：

- 连续收到多个 TCP 包时，必须从当前缓冲区起点重新解析包头，不能复用已经前移的数据流读位置。
- 中文发送长度必须按 UTF-8 字节计算，否则长度字段与实际包体不一致。
- 文本气泡测量要考虑文档、布局边距及小数取整，否则最后一个字可能意外换行。

代码中的修复痕迹不证明你独立定位过，也不证明运行测试已经通过；介绍时按自己的真实经历和验证记录表述。

### 25. 你如何验证项目？

区分静态阅读、编译、单模块测试、端到端联调、压测。面试可提出以下验证方案，但执行前不要说已经全部通过：

- 协议：拆开包头、拆开包体、多个包一起发送；非法长度与未知 ID；中文和空内容；中途断开。
- 登录：正确账号、错误密码、错误 Token、服务不可用、超时、重复登录。
- 验证码：正常、错误、过期、重复提交、Redis 故障、SMTP 慢响应。
- 界面：长文本、换行、窗口缩放、大图、连续滚轮、反复打开关闭。
- 性能：记录环境、连接数、发送频率、消息大小、错误率、延迟分位数、CPU 与内存；区分空闲连接规模和活跃请求吞吐量。

## 七天复习顺序（校招 / 实习，客户端与后端都准备）

1. 第一天：把项目介绍和完整登录链路讲顺，画出四个服务及 MySQL、Redis。
2. 第二天：读 TcpMgr、CSession，手画三次收包如何组成两条消息。
3. 第三天：读 LogicSystem、AsioIOServicePool，标出每个回调在哪个线程、锁保护哪些数据。
4. 第四天：读连接池和资源守卫，练习条件变量、智能指针、RAII、单例追问。
5. 第五天：梳理验证码、密码校验、Token 与节点分配，记清当前限制。
6. 第六天：读气泡、滚动、无边框窗口代码；准备一段真实的问题定位经历。
7. 第七天：脱离代码做一轮模拟面试；答不清的地方回到真实调用链，不补虚构性能或业务成果。

Qt 岗优先练 17—22 题；后端岗优先练 4—16 题；所有岗位都要会 1—3、23—25 题。
